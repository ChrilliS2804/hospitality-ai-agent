## Phase 1: MVP — Restaurant Reservation Agent

### Sprint 1 — Foundation and Infrastructure Skeleton (2 weeks)

**Goal**: Working AWS environment, repo structure, CI/CD pipeline, and a "hello world" Lambda reachable from Amazon Connect.

**Tasks**:
- [ ] INFRA-001: Scaffold monorepo structure (all directories, pyproject.toml, Makefile)
- [ ] INFRA-002: Terraform backend setup (S3 + DynamoDB state, dev environment)
- [ ] INFRA-003: Terraform networking module (VPC, subnets, VPC endpoints)
- [ ] INFRA-004: Terraform security module (KMS keys, base IAM policies)
- [ ] INFRA-005: Terraform DynamoDB module (single global table with GSIs, TTL, KMS, backups)
- [ ] INFRA-006: Terraform Lambda module (call-handler skeleton, IAM role, log group)
- [ ] INFRA-007: Amazon Connect instance provisioned via Terraform
- [ ] INFRA-008: Basic Contact Flow — inbound call → Lambda → return greeting
- [ ] CICD-001: GitHub Actions — python.yml (ruff, mypy, pytest)
- [ ] CICD-002: GitHub Actions — terraform.yml (fmt, validate, plan)
- [ ] CICD-003: GitHub Actions — deploy-dev.yml (terraform apply + Lambda deploy)
- [ ] SHARED-001: shared library skeleton (logging, tracing, base exceptions, AWS clients)
- [ ] SPIKE-001: Validate Connect → Lambda → Bedrock round-trip latency

**Definition of Done**: Call a phone number, hear a greeting generated by Lambda, see the invocation in CloudWatch.

---

### Sprint 2 — AI Conversation Engine (2 weeks)

**Goal**: Multi-turn conversation with intent classification and slot filling via Bedrock.

**Tasks**:
- [ ] AI-001: Bedrock client wrapper in shared library (invoke_model, error handling, retry)
- [ ] AI-002: System prompt design for hospitality reservation agent
- [ ] AI-003: Intent classification (MAKE_RESERVATION, CANCEL, MODIFY, FAQ, HANDOFF, UNKNOWN)
- [ ] AI-004: Slot filling logic (date, time, party_size, guest_name, phone, email)
- [ ] AI-005: Conversation state model (ConversationSession domain entity)
- [ ] AI-006: DynamoDB session repository (read/write session state)
- [ ] AI-007: Multi-turn conversation loop in Call Handler
- [ ] AI-008: Clarification and re-prompt logic (max 3 retries per slot)
- [ ] AI-009: Unit tests for intent classification and slot filling (mocked Bedrock)
- [ ] AI-010: Integration test — full conversation flow against dev environment

**Definition of Done**: Agent can conduct a multi-turn conversation, classify intent, collect all reservation slots, and confirm back to caller.

---

### Sprint 3 — Reservation Service (2 weeks)

**Goal**: Full reservation CRUD with availability checking, persisted to DynamoDB.

**Tasks**:
- [ ] RES-001: Reservation domain model (entity, value objects, status enum)
- [ ] RES-002: Repository interface (IReservationRepository)
- [ ] RES-003: DynamoDB repository implementation
- [ ] RES-004: CreateReservationUseCase (with availability check)
- [ ] RES-005: CancelReservationUseCase
- [ ] RES-006: ModifyReservationUseCase (check new slot availability)
- [ ] RES-007: GetReservationUseCase (by ID and by phone+date)
- [ ] RES-008: CheckAvailabilityUseCase
- [ ] RES-009: Reference number generation (human-readable, e.g. RES-2026-0531-001)
- [ ] RES-010: Reservation Service Lambda handler and IAM role
- [ ] RES-011: Unit tests — all use cases (mocked repository)
- [ ] RES-012: Integration tests — DynamoDB repository (moto)
- [ ] RES-013: Wire Call Handler → Reservation Service (Lambda invoke)

**Definition of Done**: End-to-end call creates a reservation in DynamoDB with correct data and reference number.

---

### Sprint 4 — Notifications and FAQ (2 weeks)

**Goal**: SMS/email confirmations delivered to guests; FAQ questions answered from knowledge base.

**Tasks**:
- [ ] NOTIF-001: Terraform messaging module (SNS topics, SES config, EventBridge bus)
- [ ] NOTIF-002: Notification Service Lambda (EventBridge trigger)
- [ ] NOTIF-003: SMS notification via SNS (reservation created, cancelled, modified)
- [ ] NOTIF-004: Email notification via SES (reservation created, cancelled, modified)
- [ ] NOTIF-005: Notification templates (configurable per tenant)
- [ ] NOTIF-006: EventBridge rule — ReservationCreated → Notification Service
- [ ] NOTIF-007: Dead letter queue for failed notifications
- [ ] NOTIF-008: Unit and integration tests for notification service
- [ ] FAQ-001: Terraform Bedrock Knowledge Base module (S3 + OpenSearch Serverless)
- [ ] FAQ-002: FAQ Service Lambda (query Knowledge Base)
- [ ] FAQ-003: Sample FAQ document ingestion (opening hours, menu basics)
- [ ] FAQ-004: Wire Call Handler → FAQ Service for FAQ intent
- [ ] FAQ-005: Fallback to human handoff when no FAQ answer found
- [ ] FAQ-006: Unit and integration tests for FAQ service

**Definition of Done**: Caller receives SMS and email after booking; FAQ questions answered correctly from knowledge base.

---

### Sprint 5 — Human Handoff and Call Summarization (2 weeks)

**Goal**: Seamless escalation to human agents; call summaries generated and stored.

**Tasks**:
- [ ] HANDOFF-001: Handoff Service Lambda
- [ ] HANDOFF-002: Escalation trigger detection (explicit request, repeated failure, low confidence)
- [ ] HANDOFF-003: Amazon Connect call transfer via Contact Flow
- [ ] HANDOFF-004: Callback request flow (no agent available)
- [ ] HANDOFF-005: Staff notification via SNS on handoff
- [ ] HANDOFF-006: Call summary generation (Bedrock summarization prompt)
- [ ] HANDOFF-007: Summary stored in DynamoDB session record
- [ ] HANDOFF-008: Unit and integration tests for handoff service
- [ ] OBS-001: CloudWatch custom metrics (all defined metrics emitted)
- [ ] OBS-002: CloudWatch alarms (all defined alarms configured via Terraform)
- [ ] OBS-003: X-Ray active tracing on all Lambdas
- [ ] OBS-004: CloudWatch dashboard (call volume, resolution rate, latency)

**Definition of Done**: Caller can request human; call transfers correctly; summary stored; all metrics visible in CloudWatch dashboard.

---

### Sprint 6 — Hardening, Test Environment, and MVP Release (2 weeks)

**Goal**: Production-quality code, test environment deployed, MVP ready for pilot.

**Tasks**:
- [ ] HARD-001: PII masking in all log statements
- [ ] HARD-002: Input validation hardening (all Lambda inputs validated via Pydantic)
- [ ] HARD-003: Error handling review — all Lambdas return graceful errors to Connect
- [ ] HARD-004: Provisioned Concurrency on Call Handler Lambda
- [ ] HARD-005: Lambda timeout and memory tuning (based on Sprint 1–5 metrics)
- [ ] HARD-006: DynamoDB capacity review (on-demand confirmed; alarms set)
- [ ] HARD-007: Secrets Manager — all credentials migrated from env vars
- [ ] HARD-008: KMS encryption verified on all data stores
- [ ] INFRA-009: Terraform test environment (deploy-test.yml pipeline)
- [ ] TEST-001: End-to-end integration test suite (full call flow)
- [ ] TEST-002: Load test (100 concurrent calls simulation)
- [ ] DOCS-001: Local dev setup runbook
- [ ] DOCS-002: Deployment runbook
- [ ] DOCS-003: Troubleshooting runbook
- [ ] CICD-004: deploy-prod.yml pipeline with manual approval gate
- [ ] CICD-005: Blue/green Lambda deployment with canary traffic shifting

**Definition of Done**: MVP deployed to test environment; all integration tests pass; load test meets NFRs; runbooks complete; prod pipeline ready.
